# API 계약 변경 점검

이전 OpenAPI 스펙과 새 스펙을 비교해 **계약 관점의 변경**을 정리합니다. 코드를 수정하거나 배포하지 않고, 클라이언트가 깨질 수 있는 지점과 확인 순서를 리포트로 만듭니다.

## 전제

- 이전·새 OpenAPI 3.x 스펙 파일이 있어야 합니다. JSON과 YAML을 지원합니다.
- Swagger 2.0, GraphQL SDL, 실제 런타임 응답 비교는 1차 범위가 아닙니다. 필요하면 먼저 변환하거나 별도 질문으로 남깁니다.
- 스펙에 없는 게이트웨이 정책, 인증 서버 동작, 실제 응답, 클라이언트 구현은 이 리포트만으로 판정하지 않습니다.
- 서비스명, 배포 버전, 영향을 받는 클라이언트 목록을 사용자에게 확인합니다.
- 원본 스펙은 덮어쓰지 않습니다. 결과는 별도 디렉터리에 씁니다.

## 비교 규칙

| 심각도 | 기준 | 예 |
| --- | --- | --- |
| breaking | 기존 클라이언트가 그대로 동작하기 어려운 변경 | 경로·오퍼레이션 제거, 필수 요청 필드 추가, 응답 필드 제거, 타입 변경, enum 값 제거, 필수 파라미터 추가, 인증 요구 추가, 응답 상태 코드 제거 |
| risky | 클라이언트 구현·정책에 따라 깨질 수 있는 변경 | 요청 필드 제거, 응답 enum 값 추가, 제약 조건 변경, format 변경, operationId 변경, 서버 URL 변경, 요청 본문 제거 |
| non-breaking | 기존 클라이언트가 무시하거나 계속 사용할 수 있는 추가 | 경로·오퍼레이션 추가, 선택 요청 필드 추가, 응답 필드 추가, 응답 상태 코드 추가, 미디어 타입 추가, 인증 제거 |
| info | 계약 동작과 직접 관련 없는 변경 | 스펙 버전, deprecated 표시 |

### 우선순위

Google Issue Tracker의 P0~P4 기준을 API 계약 변경에 맞게 조정합니다. 심각도와 우선순위는 다르며, breaking이 항상 P0는 아닙니다.

| 우선순위 | 기준 | API 변경 예 |
| --- | --- | --- |
| P0 | 전체 API나 핵심 기능이 모든 클라이언트에서 즉시 불가하고 우회가 없음 | 모든 API 경로 제거 |
| P1 | 배포 전 수정 필요. 요청이 거부되거나 핵심 호출이 실패함. 우회는 가능하지만 배포 조정이 필요 | 필수 요청 필드·파라미터 추가/제거, 전역 인증 추가, 요청 enum 제거 |
| P2 | 배포 전 확인. 응답 소비 문제이거나 우회 가능한 breaking. 기본값 | 응답 필드 제거, 응답 enum 제거, 상태 코드 제거 |
| P3 | 호환성 확인. 클라이언트 구현에 따라 영향이 있을 수 있음 | 제약 조건 변경, operationId 변경, 응답 enum 추가, 서버 URL 변경 |
| P4 | 참고. 기존 클라이언트가 그대로 동작함 | 새 경로·필드, 문서 버전 |

- P0는 전면 중단이 명백할 때만 씁니다. 스펙만 보고 확실하지 않으면 P1부터 검토합니다.
- P1·P2는 breaking, P3는 risky, P4는 non-breaking·info를 기본으로 합니다.
- 이 우선순위는 **리뷰 우선순위**입니다. 실제 사용량·핵심 경로·우회 가능성에 따라 팀에서 올리거나 내릴 수 있습니다.

- 분류는 **스펙 기준**입니다. 같은 변경도 실제 게이트웨이·클라이언트에 따라 다를 수 있습니다.
- 요청 방향과 응답 방향을 구분합니다. 요청의 필수 필드 추가와 응답의 필드 제거는 모두 breaking입니다.
- enum 값 추가는 요청이면 non-breaking, 응답이면 risky로 봅니다. 응답에 새 값이 나올 때 클라이언트가 처리해야 하기 때문입니다.
- 확실하지 않은 변경은 `risky`로 두고 `## 확인이 필요한 것`에 질문으로 남깁니다.

## 절차

1. 이전·새 스펙 경로, 서비스명, 배포 버전, 영향 클라이언트를 확인합니다.
2. 두 스펙이 OpenAPI 3.x인지 확인합니다. `openapi` 필드가 없거나 2.x이면 중단하고 변환 여부를 질문합니다.
3. 비교를 실행합니다.

   `python3 <스킬 폴더>/scripts/api_diff.py --old <이전 스펙> --new <새 스펙> --service <서비스명> --release-version <버전> --clients <클라이언트 목록> --out docs/api/<service>/api-diff.md --json-out docs/api/<service>/api-diff.json`

4. 결과의 `## 먼저 확인할 것`에서 P0·P1·P2를 먼저 읽고, `## API별 변경`·`## 공통 변경`으로 실제 클라이언트 사용처와 배포 순서를 확인합니다.
5. P3는 클라이언트 파서·SDK 생성·게이트웨이·권한 정책과 함께 검토합니다.
6. 외부 `$ref`, 해석하지 못한 스펙, 런타임 차이는 `## 확인이 필요한 것`으로 남깁니다.
7. `## 배포 전 체크리스트`와 `## 테스트 체크리스트`를 실제 배포 순서에 맞게 보정합니다.
8. `--fail-on-breaking`을 쓰면 breaking이 있을 때 exit 1로 CI에서 차단할 수 있습니다.
9. 결과를 요약합니다. P0~P4 건수, 영향 경로, 클라이언트 배포 순서, 확인 필요 항목을 보고합니다.
10. 리포트 옆의 `api-diff.artifact.json`에서 `sources`가 실제 스펙 경로와 맞는지 확인합니다. 스펙이 `openapi/` 아래 여러 파일로 나뉘면 `--sources openapi/**`처럼 넓혀 다시 생성합니다.

## 출력 형식

`docs/api/<service>/api-diff.md`:

- 상단 메타데이터: 서비스, 비교 스펙·버전, 배포 버전, 영향 클라이언트, 생성 시각, 집계
- `## 먼저 확인할 것`: `P0`·`P1`·`P2` 변경을 사용자 영향 문장과 영향 API로 요약
- `## API별 변경`: 엔드포인트별로 변경과 영향을 한 줄씩 표시
  - 각 줄 앞에 `P0`(전면 중단)·`P1`(배포 전 수정)·`P2`(배포 전 확인)·`P3`(호환성 확인)·`P4`(참고) 중 하나를 붙임
  - `요청`, `응답 200`, `SDK`, `API`처럼 변경 위치를 먼저 표시
  - body 예시가 바뀌면 엔드포인트 아래에 `이전 → 이후` JSON diff를 넣고, `-`는 이전 값, `+`는 이후 값으로 표시
- `## 공통 변경`: 인증·서버·문서 버전처럼 특정 엔드포인트에 속하지 않는 변경
- `## 배포 전 체크리스트`
- `## 테스트 체크리스트`
- `## 확인이 필요한 것`
- `## 부록: 전체 변경 목록`: finding ID·우선순위·위치·변경을 모두 기록

심각도를 P0~P4에 그대로 대응시키지 않습니다. breaking은 P0(전면 중단)·P1(배포 전 수정)·P2(배포 전 확인)로 나누고, risky는 P3, non-breaking·info는 P4로 둡니다. 상단에 우선순위 범례와 P0~P4 집계를 표시합니다. 위치는 `GET /shares → 응답 200 본문 → ownerEmail`처럼 메서드·경로·요청/응답 본문·필드 순서로 씁니다.

`api-diff.artifact.json`은 산출물 옆에 남기는 sidecar manifest입니다. `sources`(기본: 이전·새 스펙 경로), `generated_commit`, `regenerate`를 기록해 `gorani-change-impact`가 갱신 필요 여부를 판단하게 합니다.

`api-diff.json`은 같은 findings를 기계적으로 읽을 수 있게 저장합니다.

| 필드 | 내용 |
| --- | --- |
| `summary` | 심각도별 건수 |
| `priority_summary` | P0~P4 우선순위별 건수 |
| `findings` | `id`, `severity`, `priority`, `area`, `location`, `message`, `old`, `new`, `action` |
| `body_changes` | 오퍼레이션·방향·상태·미디어 타입·이전/이후 스키마 형태·`old_example`·`new_example`·예시 변경 여부 |
| `unresolved_refs` | 해석하지 못한 `$ref` |

- finding ID는 `B-01`, `R-01`, `N-01`, `I-01`처럼 심각도별로 부여합니다.
- `old`·`new`에는 이전·이후 타입, 필수 여부, enum 값, 제약 조건을 기록합니다.
- 실제 코드나 스펙을 수정하지 않습니다.
- `--out -`으로 stdout에만 쓸 때는 `--manifest`를 주지 않으면 sidecar manifest를 만들지 않습니다.

## 입력과 옵션

| 옵션 | 내용 |
| --- | --- |
| `--old`, `--new` | 비교할 OpenAPI 3.x JSON/YAML |
| `--out` | Markdown 경로. `-`이면 stdout |
| `--json-out` | findings JSON 경로 (선택) |
| `--service` | 서비스명 |
| `--release-version` | 배포 버전 |
| `--clients` | 영향 클라이언트 목록 (쉼표 구분) |
| `--sources` | 산출물 갱신 판단에 쓸 소스 글롭 (쉼표 구분). 기본은 이전·새 스펙 경로 |
| `--manifest` | sidecar `.artifact.json` 경로. 기본은 리포트 옆 |
| `--no-manifest` | sidecar manifest를 만들지 않음 |
| `--fail-on-breaking` | breaking이 있으면 exit 1 |

## 도구 설치

필요한 프로그램이 없으면 자동 설치를 시도합니다.

- OS 패키지 관리자(macOS `brew`, Debian/Ubuntu `apt-get`, Fedora `dnf`, Arch `pacman`, Windows `winget`·`choco`·`scoop`)와 언어 패키지 관리자(`uv`·`pipx`·`npm`·`cargo`·`go`)를 우선합니다.
- 작업에 필요한 도구만 설치합니다. 무관한 패키지나 전체 도구 묶음을 설치하지 않습니다.
- 설치 전에 도구와 명령을 알립니다. 사용자가 설치를 거부하면 설치하지 않고 대체 도구나 입력 파일을 요청합니다.
- 사용자 권한 설치를 우선합니다. `sudo`가 필요하면 `sudo -n`으로만 시도하고 암호 입력을 요구하지 않습니다. 실패하면 실행할 명령과 이유를 보고합니다.
- 공식 패키지·저장소만 사용합니다. `curl | sh`, 출처 불명 바이너리, 임의 URL 다운로드·실행을 금지합니다.
- 설치 후 `command -v`와 `--version`으로 확인합니다. 실패하면 대체 도구를 쓰거나 입력 파일을 요청합니다.
- 설치한 도구·버전·실패 사유를 결과나 evidence에 기록합니다.
- 문서·고객 데이터를 설치 과정에서 외부로 보내지 않습니다.
- GUI 앱·드라이버·커널·서비스처럼 시스템 변경이 큰 설치는 먼저 확인합니다.

## 실패 처리

- JSON/YAML 파싱이 실패하면 스펙 경로와 오류 위치를 보고하고 중단합니다.
- YAML 파서가 없으면 PyYAML 설치를 시도하고, 실패하면 JSON 변환본을 요청합니다.
- 외부 `$ref`나 해석할 수 없는 `$ref`가 있으면 `risky`로 표시하고, 외부 스펙 포함 여부를 질문합니다.
- 경로나 오퍼레이션이 0개면 스펙이 비어 있는지 확인하고, 비교 결과를 완료로 보고하지 않습니다.
- 변경이 없으면 “breaking 없음, 변경 없음”을 보고합니다. 점검 항목을 억지로 만들지 않습니다.
- `--fail-on-breaking`이 1을 반환하면 실패가 아니라 배포 전 확인이 필요하다는 뜻입니다. breaking 목록을 먼저 보고합니다.
- 실제 런타임 응답과 스펙이 다르면 스펙을 사실로 단정하지 말고 `## 확인이 필요한 것`에 적습니다.

## 금지

- 스펙에 없는 런타임 동작·클라이언트 구현을 사실처럼 쓰지 않습니다.
- 코드·스펙을 수정하거나 커밋·푸시하지 않습니다.
- breaking 후보를 근거 없이 `non-breaking`으로 낮추지 않습니다.
- enum 추가를 무조건 안전하다고 단정하지 않습니다. 응답 enum은 risky로 둡니다.
- 내부 URL, 토큰, 고객 정보를 리포트에 그대로 노출하지 않습니다. 필요하면 마스킹합니다.
- 스펙 파일을 외부 API·LLM 서비스에 무단 업로드하지 않습니다.

## 문제 보고

스킬이 예상과 다르게 실패하거나 개선점·아이디어·양식 제안이 보이면, 원인이 이 스킬·스크립트에 있는지 확인한 뒤 `gorani-report`로 GitHub 이슈를 만들지 사용자에게 먼저 묻습니다. 공개 이슈에는 고객 정보·시크릿·내부 URL을 넣지 않고, 사용자 확인 후 작성합니다.

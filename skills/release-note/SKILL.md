# 고객용 릴리스 노트 생성

git 범위의 변경을 고객이 읽을 문장으로 바꾸고, 사용자가 고른 산출물(앱 페이지·GitHub 본문·스토어 요약·내부 기록)을 만듭니다. 커밋을 그대로 나열하지 않고, 고객에게 보이는 변화만 골라 이점과 사용 방법을 설명합니다.

## 전제

- git 저장소와 이전 릴리스 지점이 있어야 합니다. 태그가 없으면 시작 지점을 사용자에게 확인합니다.
- python3 가 필요합니다. 스크립트는 표준 라이브러리만 사용합니다.
- 고객, 배포 채널, 언어를 먼저 정합니다. 기본 대상은 최종 사용자이고, 기본 언어는 한국어입니다.
- 고객에게 보이면 안 되는 내부 정보(직원 이름, 이슈 번호, 내부 URL, 보안 취약점 상세)에 접근할 수 있는 환경이어야 합니다. 결과물에는 넣지 않습니다.
- 앱스토어 글자 수 제한은 정책에 따라 바뀔 수 있습니다. 입력의 `limits` 로 조정하고, 최종 제출 화면에서 한 번 더 확인합니다.
- 릴리스 노트는 자동으로 배포하지 않습니다. 고객에게 나가기 전에 사람이 읽고 승인합니다.

## 절차

1. 릴리스 정보를 확인합니다. 제품명, 새 버전, 이전 릴리스 태그, 배포일, 고객, 채널(앱 내·백엔드·GitHub Release·앱스토어·이메일), 언어, 필요한 산출물(html, md, short, store, internal)을 정합니다.
2. 작업 디렉터리를 만듭니다. 원본 수집 JSON 은 `.release/` 에 두고, 저장소 정책에 따라 `.gitignore` 에 추가합니다.
3. 변경을 수집합니다. `python3 <스킬 폴더>/scripts/collect_changes.py --repo . --from <이전 태그> --to <대상> --product "<제품명>" --version "<버전>" --out .release/release-input.json`
4. 수집 결과를 검토합니다. 출력의 `commits`, `included`, `excluded`, `categories`, `warnings` 를 읽고, 분류가 `other` 이거나 `confidence` 가 `low` 인 항목은 diff와 PR을 직접 확인합니다.
5. 고객에게 보이는 변경을 고릅니다. 각 후보에 대해 "고객이 체감하는 변화인가", "무엇이 좋아지는가", "추가로 해야 할 일이 있는가"를 확인합니다. 내부 변경은 제외 사유를 적습니다.
6. 깨지는 변경을 찾습니다. 기존 설정·API·파일 형식·동작이 바뀌면 `breaking_changes` 로 올리고, 고객이 따라 할 수 있는 구체적인 조치를 씁니다.
7. 릴리스 노트 JSON 을 큐레이션합니다. 아래 입력 형식에 맞춰 `highlights`, `sections`, `breaking_changes`, `known_issues`, `upgrade_notes`, `support`, `short_summary`, `store_summary` 를 채웁니다.
8. 고객 문장을 씁니다. 아래 고객 문구 규칙을 적용하고, 모든 주장이 commit·diff·PR로 확인되는지 표시합니다. 확인할 수 없으면 쓰지 않습니다.
9. 결과물을 생성합니다. `python3 <스킬 폴더>/scripts/notes_build.py --input .release/release-input.json --outdir docs/releases --name release-notes --formats html,md,short,store,internal --strict`. 사용자가 고른 형식만 `--formats`에 넣습니다.
10. 검증합니다. 선택한 산출물을 읽고, 글자 수·링크·내부 정보·깨지는 변경 조치·지원 경로를 확인합니다. HTML을 선택했다면 데스크톱과 모바일 폭에서 엽니다.
11. 채널에 맞게 게시합니다. GitHub Release 본문은 md, 앱·백엔드 페이지는 html, 앱스토어는 short/store txt를 사용합니다. 게시는 사람이 승인한 뒤에 합니다.

## 입력 JSON

`collect_changes.py` 가 만든 초안을 큐레이션해 `notes_build.py` 에 넘깁니다.

최상위:

- `product`: 제품명
- `version`: 고객에게 보여 줄 버전
- `release_date`: 배포일 (YYYY-MM-DD)
- `language`: `ko` 또는 `en`. 기본 `ko`
- `audience`: 고객 설명. 예: "앱 사용자", "관리자"
- `headline`: 한 줄 요약. 선택
- `summary`: 2-3문장 요약. 선택
- `highlights`: 카드로 보여 줄 핵심 항목 배열. 각 항목은 `title`, `description`, 선택 `link`
- `sections`: `name` 과 `items` 배열. 각 item 은 `title`, `description`, 선택 `action`, 선택 `action_label`, 선택 `link`
- `breaking_changes`: `title`, `description`, 필수 `action`, 선택 `action_label`, 선택 `link`
- `action_label` 은 기본값을 바꿀 때만 씁니다. 일반 항목은 "사용 방법", 깨지는 변경은 "조치"가 기본입니다.
- `known_issues`: 문자열 배열
- `upgrade_notes`: 문자열 배열
- `support`: `url`, `email`
- `short_summary`: 스토어 짧은 버전. 없으면 자동 생성
- `store_summary`: 스토어 긴 버전. 없으면 자동 생성
- `limits`: `short`(기본 500), `store`(기본 4000)
- `commits`: 수집된 commit 배열. `included` 가 true 이면 `note`, false 이면 `reason` 을 채웁니다
- `warnings`: 수집기의 경고. 검토 후 남길 것만 둡니다
- `logs`: 실행 기록

commit 항목:

- `hash`, `short_hash`, `date`, `subject`, `body`, `files`
- `suggested_category`, `suggested_section`, `confidence`, `breaking`
- `included`: 고객 노트에 반영할지 여부
- `note`: 포함한 경우 어떤 문장에 반영했는지
- `reason`: 제외한 경우 이유

`--strict` 는 포함 commit의 `note`, 제외 commit의 `reason`, 지원 경로, 링크 형식이 빠지면 실패합니다. 수집 직후에는 note/reason 이 비어 있으므로 큐레이션 후에 사용합니다.

## 고객 문구 규칙

- 구현이 아니라 고객의 이점을 먼저 씁니다. "캐시 계층을 추가했습니다"가 아니라 "화면을 다시 열 때 더 빨리 불러옵니다"로 씁니다.
- 한 문장에 한 가지 변화만 씁니다. 길면 나눕니다.
- 무엇이 바뀌었는지, 고객에게 무엇이 좋아지는지, 필요하면 어떻게 사용하는지를 순서대로 씁니다.
- 깨지는 변경은 가장 위에 두고, 고객이 따라 할 수 있는 조치를 구체적으로 씁니다. "주의하세요"로 끝내지 않습니다.
- 제품 용어를 통일합니다. 같은 기능을 문서마다 다른 이름으로 부르지 않습니다.
- 내부 용어를 쓰지 않습니다: 리팩터링, 의존성 범프, 마이그레이션 스크립트, 내부 모듈명, 티켓 번호, 커밋 해시, 담당자 이름.
- "다양한 개선", "전반적으로 안정화" 같은 빈 문장을 쓰지 않습니다. 바뀐 점을 구체적으로 씁니다.
- 확인하지 않은 기능, 수치, 날짜, 지원 범위를 쓰지 않습니다. diff로 확인할 수 없으면 빼거나 사용자에게 묻습니다.
- 보안 수정은 공격 방법이나 재현 절차를 고객 문서에 쓰지 않습니다. "문제를 수정했습니다" 수준으로 쓰고, 공개 시점과 상세 내용은 보안 정책을 따릅니다.
- 스토어 짧은 버전은 첫 문장에 가장 큰 이점을 둡니다. 500자 안에서도 핵심 2-3개와 업그레이드 주의를 남깁니다.
- 앱 내 페이지는 스크롤이 길어도 됩니다. 대신 깨지는 변경과 지원 경로를 위·아래에 명확히 둡니다.

문장 예시:

| 입력 | 고객 문구 |
| --- | --- |
| `feat(search): add fuzzy search` | 오타가 있어도 원하는 항목을 찾을 수 있습니다. |
| `perf: reduce startup time` | 앱을 여는 시간이 짧아졌습니다. |
| `fix(auth): handle expired token` | 로그인이 갑자기 풀리던 문제를 고쳤습니다. |
| `feat!: remove legacy export` | 레거시 내보내기 기능이 종료됩니다. 새 내보내기로 옮기는 방법을 안내합니다. |
| `chore: bump dependencies` | 고객 노트에서 제외하고 내부 사유만 기록합니다. |

## 출력 형식

생성할 산출물은 사용자에게 먼저 묻고 `--formats`로 지정합니다. 기본 이름이 `release-notes`일 때 사용할 수 있는 형식은 다음과 같습니다.

| 형식 | 파일 | 채널 |
| --- | --- | --- |
| html | `release-notes.html` | 앱 WebView·백엔드 정적 페이지 |
| md | `release-notes.md` | GitHub Release 본문·이메일·문서 |
| short | `release-notes-short.txt` | 앱스토어 짧은 버전 (기본 500자) |
| store | `release-notes-store.txt` | 앱스토어 긴 버전 (기본 4,000자) |
| internal | `release-notes-internal.md` | 내부 검토용 commit 매핑·경고·확인 목록 |

사용자에게는 짧게 이렇게 묻습니다. "릴리스 노트 산출물을 선택해 주세요. 앱 페이지(html), GitHub 본문(md), 스토어 요약(short/store), 내부 검토(internal) 중 필요한 것을 알려 주세요."

- 선택한 형식만 생성하거나 갱신합니다. 선택하지 않은 기존 파일은 건드리지 않습니다.
- `internal`을 선택하지 않으면 내부 매핑 파일을 만들지 않습니다. `--strict` 검증은 그대로 수행되고, 경고·검토 항목은 콘솔 요약에 남깁니다.
- `short`·`store`를 선택한 경우에만 해당 글자 수 제한을 검사합니다. 선택하지 않은 요약이 길어도 HTML·md 생성을 막지 않습니다.
- `--formats`를 생략하면 기존 동작과 같은 전체 산출물을 만듭니다. 사용자에게 물었으면 선택 결과를 명시해 전달합니다.

HTML:

- CSS 를 인라인으로 넣고 외부 이미지·폰트·스크립트를 쓰지 않습니다. CSP 는 `default-src 'none'` 입니다.
- 깨지는 변경을 가장 먼저 강조하고, 핵심 항목 카드, 섹션별 상세, 알려진 문제, 지원 경로를 보여 줍니다.
- 라이트·다크 모드, 모바일 폭, 인쇄를 지원합니다.
- commit hash, 작성자, 내부 검토 내용은 넣지 않습니다.

md:

- 같은 내용을 평문으로 담습니다. 링크는 https 또는 mailto만 허용합니다.
- 고객 문구에 커밋 해시와 티켓 번호를 넣지 않습니다.

short·store:

- `short`는 스토어 짧은 버전, `store`는 긴 버전입니다.
- 글자 수 제한은 입력의 `limits`로 조정하고, 제출 화면에서 실제 제한을 다시 확인합니다.

internal:

- `-internal.md`는 내부용입니다. 앱 자산, 공개 페이지, 스토어에 넣지 않습니다.

종료 코드:

- 정상 0
- 입력 검증 실패 또는 `--strict` 위반 1
- argparse 인자 오류 2

## 채널별 사용

- GitHub Release: `release-notes.md` 본문을 붙이고, 제목은 제품명과 버전으로 씁니다.
- 앱 내·백엔드: `release-notes.html` 을 정적 파일로 두거나 앱 자산에 넣습니다. 파일이 자기완결이므로 네트워크 요청이 필요 없습니다.
- 앱스토어: `release-notes-short.txt` 는 500자 제한, `release-notes-store.txt` 는 4,000자 제한을 기본으로 합니다. 제출 화면의 실제 제한과 줄바꿈 처리를 확인합니다. 스토어 산출물을 쓰려면 `short`·`store`를 `--formats`에 포함합니다.
- 이메일·푸시: `short_summary` 를 쓰고 전체 노트 링크를 답니다. 푸시에는 긴 설명을 넣지 않습니다.
- 다국어: 언어별로 입력 JSON 을 따로 만들고 `language` 를 `ko` 또는 `en` 으로 지정합니다. 섹션 이름과 본문도 해당 언어로 큐레이션합니다.

## 검증

- `--strict` 로 실행해 commit 매핑, 지원 경로, 링크 형식이 모두 채워졌는지 확인합니다.
- `short_chars` 와 `store_chars` 가 제한 이하인지 확인합니다. 초과한 명시 요약은 스크립트가 실패시킵니다.
- 선택한 고객 산출물에서 커밋 해시, 이슈 번호, 직원 이름, 내부 URL이 없는지 확인합니다.
- 모든 고객 문장이 commit·diff·PR로 확인되는지 내부 매핑 표 또는 콘솔 요약과 대조합니다.
- 깨지는 변경의 `action` 이 실제로 따라 할 수 있는 수준인지 확인합니다.
- 링크가 https 또는 mailto이고 실제로 열리는지 확인합니다.
- HTML 을 데스크톱과 모바일 폭에서 열고, 페이지를 열 때 자동으로 나가는 외부 리소스 요청이 0건인지 확인합니다. 고객이 누르는 링크는 https 또는 mailto만 허용합니다.
- 앱스토어 제출 화면에서 글자 수와 줄바꿈을 다시 확인합니다.

## 실패 처리

- 이전 릴리스 태그가 없으면 추측하지 말고 사용자에게 시작 지점을 묻습니다.
- 범위에 commit 이 없으면 `--from`·`--to` 가 맞는지, merge commit 만 있는 범위인지 확인합니다.
- commit 이 너무 많으면 범위를 릴리스 단위로 좁힙니다. 한 번에 수백 개를 고객 노트로 바꾸지 않습니다.
- 분류가 불확실하거나 `other` 인 항목은 diff와 PR을 확인합니다. 그래도 고객 영향을 알 수 없으면 제외하고 사유를 적습니다.
- 깨지는 변경에 조치가 없으면 `--strict` 가 실패합니다. 조치를 쓰거나, 고객이 할 일이 없다면 그 이유를 설명합니다.
- 스토어 요약이 제한을 넘으면 문장을 줄입니다. 자동으로 잘린 경우 경고가 나오므로 그대로 제출하지 않습니다.
- 링크가 잘못되면 https 또는 mailto로 고칩니다. `javascript:` 같은 형식은 고객 페이지에 넣지 않습니다.
- 지원 경로가 없으면 지원 URL이나 이메일을 추가합니다. 고객이 문제를 겪었을 때 갈 곳이 있어야 합니다.
- HTML 이 앱 WebView에서 안 열리면 파일 복사 경로와 CSP 설정을 확인합니다. 페이지에 외부 리소스가 없는지도 확인합니다.

## 금지

- 사용자 지시 없이 커밋·푸시·태그·배포를 하지 않습니다.
- 커밋을 그대로 고객 문구로 옮기지 않습니다.
- 확인하지 않은 기능·수치·날짜·지원 범위를 쓰지 않습니다.
- 고객 문구에 commit hash, 이슈 번호, 직원 이름, 내부 URL, 내부 모듈명을 넣지 않습니다.
- 보안 취약점의 공격 방법·재현 절차·영향받는 고객 정보를 공개 문서에 쓰지 않습니다.
